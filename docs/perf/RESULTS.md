> the *relative* change and the plan shapes are the point, not the absolute milliseconds.

## Reading the numbers

- **B1** is the weakest win, as expected: one month is ~1/24 of the rows, so the bitmap index scan still visits ~2.2k heap pages; it mainly saves the full-table scan (~24k pages). An index alone is not a big lever for low-selectivity filters — the mart (B5) is.
- **B2** turns a full scan into a 20-row index range scan; this is the classic OLTP-style lookup analysts run from support tickets.
- **B3** combines partition pruning (only the June-2025 partition is touched) with an index-only scan.
- **B4** gets **no partition pruning**: it filters on `event_date_key`, not the partition key `event_at`, so every partition is probed (empty ones are cheap seq scans) and the win comes from the partial index. Filtering on `event_at` would add pruning.
- **B5** shows that for dashboards the biggest lever is pre-aggregation (4,384 mart rows instead of ~800k facts); the mart is kept additive-only so it cannot be mis-aggregated.
- Fairness caveat: both sides were warmed once, but `perf.*` copies and `core.*` tables together exceed shared_buffers (512 MB), so some "before" pages are `read` from the OS page cache rather than `hit`. That inflates "before" by I/O-timing noise of a few ms (see `I/O Timings` in the plan files), not by orders of magnitude.

## Index cost (the other side of the trade-off)

| Table | Index | Physical indexes | Size |
|---|---|---:|---:|
| `fact_order_events` | `fact_order_events_<partition>_courier_key_event_date_key_idx` | 49 | 10 MB |
| `fact_order_events` | `fact_order_events_<partition>_event_type_event_at_idx` | 49 | 168 MB |
| `fact_order_events` | `fact_order_events_<partition>_pkey` | 49 | 181 MB |
| `fact_orders` | `fact_orders_pkey` | 1 | 31 MB |
| `fact_orders` | `ix_fact_orders_created_date` | 1 | 7464 kB |
| `fact_orders` | `ix_fact_orders_customer_time` | 1 | 33 MB |
| `fact_orders` | `ix_fact_orders_merchant_id` | 1 | 7240 kB |

Partitioned-table indexes are summed over all partitions. The `(event_type, event_at)` index is almost as large as the primary key: it buys B3, but a write-heavy production table might prefer a BRIN index on `event_at` (not measured here). Indexes also slow the bulk load; `fact_orders` therefore only carries indexes that a measured query (or the pipeline's re-keying) needs.
